# SPEC.md — Lode Runner (Modernized)

A 2D modernized recreation of Doug Smith's *Lode Runner* (1983, Broderbund), built in C with raylib. Sprite-based, 1200×900 resolution, sound effects generated via rfxgen, with raylib graphics features (shaders, blending, particles, glow) used to give the classic puzzle-platformer a contemporary look.

---

## 1. Overview

The player is a treasure hunter trapped in a multi-storey vault. Each level is a static screen of bricks, ladders, and rope-bars. The player must:

1. Collect every gold piece on the screen.
2. Once all gold is collected, a hidden escape ladder appears connecting the top row to the exit.
3. Climb to the top row to advance to the next level.

The player is pursued by guards (Bungeling Empire) using a deterministic but counter-intuitive AI. The player cannot jump or attack directly — the only offensive tool is **digging** a temporary hole into a diggable brick to either pass through it, or to trap a guard.

### 2.1 Time step and movement model

The game runs at a fixed 60 fps target. All gameplay timers (dig refill, guard hole, animation, respawn) accumulate in seconds via `GetFrameTime()`.

**Actors are always either *resting on a tile* or *traversing between two adjacent tiles.*** Movement uses **continuous interpolation between cells** with a **discrete commit on arrival**:

```c
typedef struct {
    int   tile_r, tile_c;     // current tile (where the actor "is")
    int   dst_r,  dst_c;      // destination tile during traversal (== tile_* if resting)
    float t;                  // 0.0 at start of step, 1.0 at arrival
    Dir   facing;
} Actor;
```

- While `t < 1.0`, the actor is **mid-step** and its rendered pixel position is `lerp(tile, dst, t)`. Input and AI are **ignored** during a step (this is the classic "you can't change your mind mid-tile" rule).
- When `t` reaches `1.0`: snap `tile_* = dst_*`, set `t = 0`, then re-evaluate input (player) or AI (guard) to choose the next step. If no movement is requested or possible, the actor *rests* (`dst_* == tile_*`) and re-checks every frame.
- Step duration = `1 / speed_cells_per_sec` (see §4.2 table). Per frame, `t += dt * speed`.

**Collision / kill check** runs **only on tile arrival** (when an actor commits a new `tile_*`). The player dies iff, after committing, any guard's `tile_r,tile_c` equals the player's. We do not check during traversal — the snap-on-arrival model means there is no meaningful "halfway" state, and arrival-only checks avoid double-fires from two actors crossing on the same edge.

**Falling** uses the same model: a fall is a sequence of one-cell traversals downward at `FALL_SPEED`, re-evaluated on each arrival (the actor may grab a rope it falls into, see §4.2).

**Anim frames** advance independently on a fixed 8 fps timer driven by `GetFrameTime()`, so animation never desyncs from movement on slow frames.

## 3. World Tiles

The level is a **30 × 22 grid** of tiles. Each tile is one of:

| ID | Tile | Behavior |
|---|---|---|
| `EMPTY` | Air | Walkable when a solid is below; otherwise the actor falls. |
| `BRICK` | Diggable brick | Solid floor. Can be dug from adjacent tiles → becomes `HOLE`. |
| `HOLE` | Open dug pit | Behaves identically to `EMPTY` for movement. Has a refill timer; reverts to `BRICK` when it expires. Distinct enum value so the tile state is always self-consistent. |
| `SOLID` | Bedrock / concrete | Solid floor. **Cannot** be dug. |
| `LADDER` | Ladder | Climbable up/down. Acts as floor when stood on top. |
| `ROPE` | Hand-to-hand bar | Player & guards can hang and traverse left/right. Player can drop. |
| `GOLD` | Gold piece | Collectible. Removed when picked up. |
| `EXIT_LADDER` | Hidden escape ladder | Behaves as `EMPTY` until all gold is collected; then behaves as `LADDER`. |
| `TRAPDOOR` | Fake brick | Looks like `BRICK` but actors fall through. (Optional, used in later levels.) |
| `PLAYER_SPAWN` | Marker | Player start position (rendered/treated as `EMPTY`). |
| `GUARD_SPAWN` | Marker | Guard start position (rendered/treated as `EMPTY`). |

### 3.1 World data layout

```c
typedef enum {
    TILE_EMPTY, TILE_BRICK, TILE_HOLE, TILE_SOLID, TILE_LADDER, TILE_ROPE,
    TILE_GOLD, TILE_EXIT_LADDER, TILE_TRAPDOOR
} TileID;

typedef struct {
    TileID  tiles[GRID_ROWS][GRID_COLS];        // single source of truth for tile state
    float   hole_timer[GRID_ROWS][GRID_COLS];   // refill clock; meaningful only when tile == TILE_HOLE
    int     gold_remaining;                     // gold currently in the world (not in pockets)
    int     gold_total;                         // initial count, for level-cleared check
    bool    all_gold_collected;                 // latched once true for this level
    int     player_spawn_r, player_spawn_c;
    int     guard_spawn_r[MAX_GUARD_SPAWNS], guard_spawn_c[MAX_GUARD_SPAWNS];
    int     guard_spawn_count;
    int     guard_count;                        // number of guards spawned this level
} World;
```

**Single source of truth**: a tile's behavior comes from `tiles[r][c]` alone. `hole_timer` is only the countdown clock for refilling and is read by the renderer (warning pulse) and refill logic — *not* by movement code. Transitions:

- Dig: `tiles[r][c] = TILE_HOLE`, `hole_timer[r][c] = DIG_REFILL_SEC`.
- Per frame, for each `TILE_HOLE`: `hole_timer -= dt`. When it reaches 0, `tiles[r][c] = TILE_BRICK` (and any actor still on that tile dies — see §4.3, §5).

This means every movement query (`is_support(r,c)`, `is_passable(r,c)`, etc.) is a pure switch on `TileID` with no hole-timer check anywhere — eliminating the duplication risk called out in review.

### 3.2 Movement helpers

Two predicates drive all movement decisions for both player and guards:

```c
static bool tile_is_support(TileID t, bool exit_revealed) {
    // "an actor standing on the tile ABOVE this one is supported"
    switch (t) {
        case TILE_BRICK:
        case TILE_SOLID:
        case TILE_LADDER:
            return true;
        case TILE_EXIT_LADDER:
            return exit_revealed;
        default:
            return false; // EMPTY, HOLE, ROPE, GOLD, TRAPDOOR, EXIT_LADDER (hidden)
    }
}

static bool tile_is_passable(TileID t, bool exit_revealed) {
    // "an actor can move INTO this tile"
    switch (t) {
        case TILE_EMPTY:
        case TILE_HOLE:
        case TILE_LADDER:
        case TILE_ROPE:
        case TILE_GOLD:
            return true;
        case TILE_EXIT_LADDER:
            return true; // hidden: passable as empty; revealed: passable as ladder
        case TILE_TRAPDOOR:
            return true; // passable, but no support → actor falls through on arrival
        default:
            return false; // BRICK, SOLID
    }
}
```

These are the *only* tile-classification calls movement code makes. Adding a new tile type means updating these two switches — no scattered checks elsewhere.

## 4. Player

### 4.1 State

`PlayerState` represents only states that change *gameplay rules* — not animation flavor. Idle/run/up-vs-down all share the same rules (walking on a support); they're distinguished at draw time from `Actor` fields, not at update time.

```c
typedef enum {
    PSTATE_WALK,    // on a support tile (BRICK/SOLID/LADDER top); resting or stepping L/R
    PSTATE_CLIMB,   // current tile is LADDER (or revealed EXIT_LADDER); moving up/down
    PSTATE_HANG,    // current tile is ROPE; resting or traversing L/R
    PSTATE_FALL,    // no support below, not on ladder/rope; falling one cell at a time
    PSTATE_DIG,     // dig_lock_timer > 0; locked in place, dig animation playing
    PSTATE_DEAD,    // death animation running before level reset
} PlayerState;

typedef struct {
    Actor actor;              // see §2.1 — tile_r/c, dst_r/c, t, facing
    PlayerState state;
    float dig_lock_timer;     // > 0 while in PSTATE_DIG
    float death_timer;        // > 0 while in PSTATE_DEAD
} Player;
```

**Animation** is derived from `(state, actor.t > 0, actor.facing)` at draw time:

| State | `t == 0` (resting) | `t > 0` (stepping) |
|---|---|---|
| `WALK` | `player_idle` | `player_run_1..4` |
| `CLIMB` | `player_climb_1` | `player_climb_1..2` cycle |
| `HANG` | `player_hang_1` | `player_hang_1..2` cycle |
| `FALL` | (n/a) | `player_fall` |
| `DIG` | `player_dig` | (n/a — locked) |
| `DEAD` | death-fade frames | (n/a) |

This keeps `PlayerState` minimal (6 values, all distinct rule-sets) and pushes idle-vs-moving to the renderer where it belongs.

**Note**: there is no `Vector2` pixel position on `Player`. Pixel position is a derived value `lerp(tile, dst, t) * TILE_SIZE + offset`, computed in the renderer. Actor data is grid-native end-to-end.

### 4.2 Movement Rules

A "support" tile (i.e. something the player can stand on) is `BRICK`, `SOLID`, or `LADDER`, **or** the top of an `EXIT_LADDER` once revealed. Holes (a temporarily-empty tile from a dig) are *not* support — actors fall in.

- **Walk** (left/right): allowed when the tile directly below the current tile is a support tile. Moves one cell horizontally per step.
- **Climb on ladder**: when the current tile is `LADDER` (or revealed `EXIT_LADDER`), Up moves one cell up; Down moves one cell down (provided the next tile is not a non-empty solid blocking entry — a brick blocks downward, a ladder/rope/empty/gold does not).
- **Step off ladder sideways**: while on a ladder tile, pressing Left/Right walks onto an adjacent tile if that adjacent tile is `EMPTY`/`GOLD`/`LADDER`/`ROPE` and has support below (or is itself a ladder/rope).
- **Hang/Traverse on rope**: when the current tile is `ROPE`, the player hangs from it. Left/Right moves one cell along the rope (if the next cell is `ROPE` or has a support tile two cells below blocked — practically: any tile the player can fall into is fine, the rope is the support). Down drops the player off the rope; the player then falls.
- **Mount a rope while falling**: if a falling player passes through a `ROPE` tile, they automatically grab it (matches the original).
- **Fall**: when the current tile has no support below and the current tile is not `LADDER`/`ROPE`. Falls one cell at a time at fall speed; no fall damage. While falling the player cannot dig and only minimally steers (cannot change column).
- **No jump.** There is no vertical input that lifts the player off a floor without a ladder.

**Speeds** (tunable; values are cells per second):

| Motion | Cells/sec | Time per cell |
|---|---|---|
| Walk | 6.0 | 0.167 s |
| Climb (up/down ladder) | 5.0 | 0.200 s |
| Hang traverse (rope) | 6.0 | 0.167 s |
| Fall | 8.0 | 0.125 s |
| Guard walk | 4.5 | 0.222 s |
| Guard climb | 3.75 | 0.267 s |
| Guard hang | 4.5 | 0.222 s |
| Guard fall | 8.0 | 0.125 s |

Guards move at 75% of player speed on every motion type (~25% slower as stated in §5).

### 4.3 Digging

- Inputs: `Z` digs the brick down-and-to-the-left; `X` digs the brick down-and-to-the-right. (`J` / `K` are accepted as secondary bindings for retro feel.)
- Required conditions, **all** must hold:
  1. Target tile = (player_row + 1, player_col ± 1) is `TILE_BRICK`. (Cannot dig `HOLE` either — it's already open.)
  2. The tile directly above the target — i.e. (player_row, player_col ± 1) — is `TILE_EMPTY` or `TILE_HOLE`. (No ladder, rope, gold, brick, or solid.)
  3. The player is currently in a walk state (standing on a support). Cannot dig while on a rope, climbing, or falling.
  4. No guard currently occupies the target tile.
- **Effect**: `tiles[target] = TILE_HOLE`, `hole_timer[target] = DIG_REFILL_SEC` (6.0 s). When `hole_timer` drops below `DIG_REFILL_SEC − DIG_WARN_PULSE_AT` (1.5 s remaining) the rim pulses; below 0.5 s it flashes red; at 0 the tile reverts to `TILE_BRICK` and `refill.wav` plays.
- **Player lock**: the player is locked in place for `DIG_LOCK_SEC = 0.25 s`, during which the dig animation plays and `dig.wav` is triggered once at the start.
- **Trapped guard**: a guard occupying a hole when it refills dies (see §5.5 respawn). `guard_die.wav` plays.
- **Trapped player**: if the player is in a hole when it refills, the player dies and the level resets (see §4.4).
- A new dig cannot target a tile that already has a guard standing on it (the dig fails silently — matches original).

Hole rendering: while `HOLE`, the tile is drawn as `EMPTY` with a thin dark rim (debris on edges) so it reads visually as "an open pit". The renderer also tints the rim red during the warning phase.

### 4.4 Lives & Death

Lives and score do **not** live on `Player`. They live on `RunStats` (see §11.3) which is owned by `game.c` and persists across player deaths and level transitions. `Player` itself is reset on every life lost.

- Start with **5 lives** (`RunStats.lives`).
- **Death triggers**:
  1. A guard occupies the same tile as the player (see overlap rule below).
  2. The player is in a hole when it refills.
- **Overlap / kill rule**: an enemy "catches" the player when, after both have committed their per-frame movement, their grid cells are equal. Pixel-AABB overlap is *not* used — using grid cells avoids flicker-edge cases at high speeds.
- **On death**: `player.state = PSTATE_DEAD`, `death_timer = 0.6 s`. While dead, the player sprite fades and a small particle burst plays. When `death_timer` expires, `game.c` decrements `RunStats.lives` and either resets the level (gold positions, guards, all dig/hole state — `RunStats` is preserved) or transitions to `SCREEN_GAME_OVER` if lives reached 0.
- **Extra life rewards**: +1 to `RunStats.lives` per level cleared. (No score-threshold extras in v1.)

## 5. Guards (Enemies)

### 5.1 Number per Level

Variable per level (1–5 in the early game, up to ~6 in later levels). Configured per-level in the level data.

### 5.2 AI Algorithm (faithful to original)

Guards do **not** A*-pathfind. Each guard re-decides its next direction at every tile arrival, using the **per-row pursuit table** algorithm below — a deterministic procedure that reproduces the original's "smart but counter-intuitive" behavior, including the move-away-on-shared-ladder quirk.

#### 5.2.1 Per-row pursuit precomputation

Once per level (and once per dig event that mutates the grid), we compute a 2D table:

```c
typedef enum { PURSUE_LEFT, PURSUE_RIGHT, PURSUE_UP, PURSUE_DOWN, PURSUE_NONE } PursuitDir;
PursuitDir pursuit[GRID_ROWS][GRID_COLS]; // "from this tile, which direction takes you closer to the player?"
```

Build with a **breadth-first flood fill from the player's tile** over the actor-traversal graph (edges = legal one-cell moves: walk on a support, climb a ladder, hang traverse, fall). Each tile's `pursuit[r][c]` is the direction of the *first edge* on the shortest path back to the player.

Cost: ~660 nodes (30×22), trivial. Recomputed cheaply when the player moves to a new tile or a hole opens/closes.

If a tile is unreachable from the player, `pursuit[r][c] = PURSUE_NONE`.

#### 5.2.2 Direction score (per-guard, per tile-arrival)

For each candidate direction `d ∈ {LEFT, RIGHT, UP, DOWN}` whose move is legal (target tile passable per §3.2 plus the climb/hang/fall constraints from §4.2):

| Term | Value | Notes |
|---|---|---|
| **Pursuit match** | +100 if `d == pursuit[guard.r][guard.c]`, else 0 | The "smart" core. Uses the precomputed table — no ad-hoc ladder hunting in the AI itself. |
| **Vertical bias** | +10 if `d` reduces `|guard.r − player.r|` | Tiebreaker: prefer closing vertical gap. |
| **Horizontal bias** | +5 if `d` reduces `|guard.c − player.c|` | Tiebreaker: prefer closing horizontal gap. |
| **Stacking penalty** | −15 if the destination tile is currently occupied (or being entered) by another guard | Source of the "move away on shared ladder" emergent behavior — when stacking penalty exceeds the small bias terms but pursuit doesn't apply, the guard picks a different direction. |
| **Fall preference** | +20 if `d == DOWN` and the resulting fall lands within 4 rows of the player | Guards drop off ledges to chase, like the original. |
| **Stable jitter** | `(hash(guard.seed, guard.r, guard.c) % 4) − 2` | Per-guard, per-tile deterministic tie-break in [−2, +1]. Each guard has a fixed `uint32_t seed` set at spawn. |
| **Idle penalty** | −1000 for `PURSUE_NONE` direction (i.e. picked when player is unreachable from this tile) | Forces guards to still pick *something* legal rather than freezing — but only if all positive-score moves are illegal. |

Pick the highest-scoring legal direction. If no direction is legal (boxed in), the guard rests for one tick and re-evaluates next arrival.

#### 5.2.3 Why this works

- **Splitting**: two guards on similar tiles get the same `pursuit` direction, but the stacking penalty diverts the second one to a different (still legal) direction.
- **Move-away-on-shared-ladder**: when both player and guard are on the same ladder, every direction has zero pursuit value (player is *on* the path, not in any direction from the guard), the small bias terms barely move, and the −15 stacking penalty (since "destination is the player's tile" counts as occupied) selects a direction *away* from the player. Exactly the classic quirk.
- **Counter-intuitive routes**: the table is BFS, so guards take the *shortest* path on the traversal graph, not the Cartesian shortest path. A guard with the player two rows up but no nearby ladder will walk *away* horizontally to reach a ladder column, looking deliberate without being clairvoyant.

#### 5.2.4 Recompute triggers

`pursuit` is rebuilt only when:
- Player commits a new tile (most common).
- A `TILE_HOLE` opens or closes (changes graph edges).
- Level loads.

Guards read the table; they do not own pathfinding state. If the player is mid-step (`t < 1`), guards use the player's `tile_*` (origin), not `dst_*` — a one-tick lag that matches arcade pacing.

### 5.3 Guard Movement Constraints

- Same tile rules as player (walk, climb, hang, fall).
- Move ~25% slower than the player on flat ground.
- Cannot dig.
- Falling into a hole: stuck for **3.0 s**, struggles, then climbs out — *unless* the hole refills first, in which case the guard dies.

### 5.4 Gold Carrying

- A guard walking over a `GOLD` tile picks it up with **50% probability** (one piece max per guard). The tile becomes `EMPTY` immediately on pickup; the gold is now considered "in the guard's pocket".
- Carried gold is rendered as a small glowing dot above the guard's head.
- **Drop conditions** (any of):
  - The guard falls into a hole — gold drops at the guard's previous tile and re-enters the world as `GOLD` (player must still collect it).
  - The guard dies — same drop behavior.
  - Random drop: each guard checks once per second; **8% chance** to drop the gold at its current tile if that tile is `EMPTY`.
- Gold-in-pocket is **not** counted toward the "all gold collected" condition; the level can only be cleared once every gold piece is back in the world AND collected by the player.

### 5.5 Respawn

When a guard dies (refilled hole), after `GUARD_RESPAWN_SEC = 1.0 s` it respawns at a random `GUARD_SPAWN` tile selected uniformly from the level's spawn tiles. If a chosen spawn tile is currently occupied (player or another guard), the next-random spawn is tried; if all are occupied the respawn is delayed by another 1.0 s. Any gold the dead guard was carrying remains dropped at the death tile.

## 6. Levels

### 6.1 Level Format

Levels are stored as plain-text `.txt` files in `src/assets/levels/`, one char per tile:

```
.   EMPTY
B   BRICK
S   SOLID
H   LADDER (think "H" shape)
-   ROPE
$   GOLD
E   EXIT_LADDER (hidden until all gold collected)
T   TRAPDOOR
P   PLAYER_SPAWN  (rendered as EMPTY at runtime)
G   GUARD_SPAWN   (rendered as EMPTY at runtime)
```

**Validation rules**, enforced at load time (failure logs an error and falls back to a built-in level):

- File must contain exactly **22 lines** of exactly **30 characters** each (no trailing whitespace counted).
- Exactly **one** `P` tile (player spawn).
- **At least one** `G` tile if the level should have guards (the count of `G` tiles is the guard count for that level — no separate metadata needed).
- **At least one** `$` tile (a level with no gold can be cleared instantly — allowed for tutorial level 1 only).
- At least one `E` tile in the top three rows (rows 0–2) so the exit ladder is reachable.

Lines may be followed by `\n` or `\r\n`. Comments are not supported in v1 (keep parser KISS).

The `EXIT_LADDER` tiles are loaded into `World.tiles` as a distinct enum value but treated as `EMPTY` for rendering and movement until `world.all_gold_collected == true`. Once revealed they behave identically to `LADDER`.

### 6.2 Level Set

We ship **10 hand-designed levels** at launch (`level01.txt` … `level10.txt`). Difficulty progression:

- L1: tutorial — gold on floor, no guards.
- L2: introduce ladders, 1 guard.
- L3: introduce ropes, 1 guard.
- L4: introduce digging-required gold, 2 guards.
- L5: digging through multiple layers (need wider gap = more layers).
- L6–L8: combinations with 3+ guards.
- L9: trapdoor introduction.
- L10: boss-feel level with 4 guards and tight passages.

### 6.3 Multi-Layer Digging

Faithful to the original: to dig through *N* stacked brick layers, the gap must be at least *N* wide. The dig logic doesn't enforce this directly; it falls out of the rule that *each dig requires `EMPTY` above the target*. To go deeper, the player must dig adjacent columns first.

### 6.4 Level Completion

- **Goal**: collect every `GOLD` tile (including any held by guards — they must drop and the player must pick them up), then reach **row 0** at any column.
- When the last gold is collected: `world.all_gold_collected = true`, `gold_complete.wav` plays, and `EXIT_LADDER` tiles reveal with a 0.6 s fade-in (see §9.2 exit-reveal shader).
- When the player's tile reaches row 0 *while* `all_gold_collected` is true: `level_clear.wav` plays, +1 life, score += 1500, then transition to `SCREEN_LEVEL_CLEAR` (1.5 s celebration screen) → next level.
- If the player reaches row 0 *before* collecting all gold, nothing happens.

### 6.5 After Level 10

After clearing level 10, the game shows a "VICTORY" screen on `SCREEN_LEVEL_CLEAR` (held until input), then loops back to level 1 with the score and lives preserved (a small "+ NEW GAME +" indicator). Speed scaling for repeated playthroughs is out of scope for v1.

## 7. HUD

Drawn in the top 108 px strip, full window width:

- **Score** (left, x ≈ 40, y ≈ 38) — `SCORE 001250`. Score events:
  - +100 per gold collected by the player (`SCORE_GOLD`)
  - +250 per guard killed by hole-refill (`SCORE_GUARD_KILL`)
  - +1500 per level cleared (`SCORE_LEVEL_CLEAR`)
- **Lives** (center) — small player-icon glyphs, one per remaining life (max 9 drawn; if more, show `×N`).
- **Level** (right, anchored x = 1160 right-aligned) — `LEVEL 03 / 10`.
- The HUD background uses a subtle vertical gradient (dark navy → black) and a 2 px luminous bottom border (thin gold line) to separate from the play area.
- Font: raylib's default font at 28 px for v1 (no custom font asset). Score uses zero-padded 6 digits.

## 8. Controls

| Action | Primary | Secondary |
|---|---|---|
| Move left | ← | A |
| Move right | → | D |
| Climb up | ↑ | W |
| Climb down / drop from rope | ↓ | S |
| Dig left | Z | J |
| Dig right | X | K |
| Pause | P | — |
| Restart level (costs a life) | R | — |
| Toggle scanline overlay | F1 | — |
| Quit to title | Esc | — |

Inputs are polled per-frame; held-direction keys produce continuous grid-step movement (the player commits one tile at a time and re-evaluates input on tile arrival).

**Pause behavior**: the game freezes the world (no timers, no AI, no animations advance), draws a translucent "PAUSED" overlay, and waits for `P` again or `Esc`. `Esc` from a paused game returns to `SCREEN_TITLE` and the run is forfeited.

**Title screen input**: Enter starts a new game, Esc quits the application. Game-over screen accepts Enter (return to title) or Esc (quit).

| `bg_cave.png` | Tiled parallax background |
| `logo.png` | Title screen logo |

Animations advance on a fixed 8 fps timer regardless of frame rate. Run-cycle frames (1..4) tick through while moving and reset to frame 1 when idle. Player and guard sprites flip horizontally based on facing direction (`DrawTextureRec` with negative source rect width).

### 9.2 raylib graphics features (modernization)

The original was monochrome blocks; we layer modern effects on top while keeping the gameplay readable:

- **Bloom on gold**: gold tiles draw with `BLEND_ADDITIVE` plus a soft glow sprite underneath. Sparkle particles on idle.
- **Hole dig effect**: brick "explodes" into ~12 dust particles using the template's `MAX_PARTICLES` budget; particles use additive blending and fade.
- **Brick refill warning**: when a hole's refill timer < 1.5 s, the surrounding brick edges pulse via a `Color` lerp; last 0.5 s flashes red.
- **Exit-reveal shader**: a simple fragment shader ramps an alpha gradient down the `EXIT_LADDER` column over 0.6 s when all gold is collected. Implemented with `LoadShaderFromMemory` (no external `.fs` file needed).
- **Subtle scanline overlay**: drawn full-screen with low alpha for retro-CRT vibe, toggleable via `F1`.
- **Camera shake**: tiny 0.15 s shake on player death (`BeginMode2D` with a randomized offset).
- **Background**: a slowly scrolling parallax cave-wall texture behind the play grid, drawn with `DrawTextureTiled` at 30% brightness.

All shaders compile-fail-safe: if a shader fails to load, the game falls back to `DrawTexture` without bloom.

## 11. Code Organization

Building on the existing template:

```
src/
  main.c          # raylib init, main loop, shutdown (existing)
  game.h          # shared state, constants, enums (extended)
  game.c          # game_init / game_update / game_draw, screen state machine
  world.h/.c      # tile grid, dig state, level loading
  player.h/.c     # player state machine, input handling, dig logic
  guard.h/.c      # guard AI, movement, gold-carry
  particles.h/.c  # dig dust + sparkles
  hud.h/.c        # score / lives / level overlay
  textures.h/.c   # texture loading & atlas (existing files extended)
  sounds.h/.c     # sound loading (existing, extend SoundID enum)
  assets/
    levels/level01.txt … level10.txt
    *.png  *.wav
```

Hot data (tile grid, guard array, particle pool) is kept in plain C structs with fixed-size arrays — no dynamic allocation in the game loop. Per AGENTS.md: stack/static for fixed sizes, KISS over DRY.

### 11.1 Screen State Machine

```c
typedef enum {
    SCREEN_TITLE,
    SCREEN_PLAY,
    SCREEN_LEVEL_CLEAR,
    SCREEN_GAME_OVER,
} ScreenID;
```

Title shows the game logo, "PRESS ENTER", and a faint demo of a guard chasing a player on a small grid in the background.

### 11.2 Cross-cutting state and tick-result contracts

Score, lives, and current screen are not gameplay state — they are *run* state. They live on a single struct owned by `game.c`:

```c
typedef struct {
    int  score;
    int  lives;
    int  level_index;       // 0..MAX_LEVELS-1
    bool scanline_overlay;  // F1 toggle
} RunStats;
```

`RunStats` is **not** touched by `player.c` or `guard.c`. Those modules report what happened during their tick via small POD return structs, and `game.c` is the only writer:

```c
typedef struct {
    bool collected_gold;     // walked over a TILE_GOLD this tick
    bool committed_new_tile; // arrived at a new tile (triggers pursuit rebuild)
    bool died;               // just entered PSTATE_DEAD (death_timer expired)
    bool reached_exit;       // arrived at row 0 with all_gold_collected
    bool dug_brick;          // started a dig this tick (for sound + particles)
} PlayerTickResult;

typedef struct {
    bool picked_up_gold;     // grabbed a TILE_GOLD this tick
    bool dropped_gold;       // a gold piece re-entered the world from this guard
    bool died_in_refill;     // killed by a brick refill — game.c awards score
    bool fell_in_hole;       // just landed in a TILE_HOLE
} GuardTickResult;

PlayerTickResult player_update(Player *p, World *w, float dt);
GuardTickResult  guard_update (Guard  *g, World *w, const Player *p, const PursuitDir pursuit[][GRID_COLS], float dt);
```

`game.c` consumes these:

```c
PlayerTickResult pr = player_update(&player, &world, dt);
if (pr.collected_gold) { stats.score += SCORE_GOLD; sounds_play(SOUND_COIN); }
if (pr.dug_brick)      sounds_play(SOUND_DIG);
if (pr.committed_new_tile) world_rebuild_pursuit(&world, player.actor.tile_r, player.actor.tile_c, pursuit);

for (int i = 0; i < world.guard_count; i++) {
    GuardTickResult gr = guard_update(&guards[i], &world, &player, pursuit, dt);
    if (gr.died_in_refill) stats.score += SCORE_GUARD_KILL;
    // ...
}

// Collisions and life/level transitions are game.c's job:
if (any_guard_on_player_tile()) start_player_death(&player);
if (pr.died) {
    stats.lives--;
    if (stats.lives <= 0) current_screen = SCREEN_GAME_OVER;
    else                   reset_level(&world, &player, guards);
}
if (pr.reached_exit) {
    stats.lives++;
    stats.score += SCORE_LEVEL_CLEAR;
    current_screen = SCREEN_LEVEL_CLEAR;
}
```

**Module dependency rule** (one direction only):

```
game.c   ──depends on──▶  player.c, guard.c, world.c, hud.c, particles.c, sounds.c
player.c ──depends on──▶  world.c
guard.c  ──depends on──▶  world.c, (Player as const read-only for tile)
hud.c    ──depends on──▶  RunStats (read-only)
```

`player.c` and `guard.c` know about `World` but **nothing about `RunStats`, `ScreenID`, or each other**. This is the only architectural decoupling we need — there is no event bus, no observer pattern, just functions returning what they did.

### 11.3 Pursuit rebuild ownership

The BFS pursuit table (§5.2.1) is read by `guard.c` but written by `world.c`. The trigger lives in `game.c`:

```c
// after player tick, if the player committed a new tile:
world_rebuild_pursuit(&world, player.actor.tile_r, player.actor.tile_c, pursuit);

// after a hole opens (dig) or closes (refill):
world_rebuild_pursuit(&world, player.actor.tile_r, player.actor.tile_c, pursuit);
```

`world_rebuild_pursuit` is a pure function of `(world, player_r, player_c)` and writes to a caller-owned `PursuitDir[ROWS][COLS]` buffer. `world.c` does not reach into `Player`; the player tile is passed by value.

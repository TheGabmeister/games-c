# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Modernized Pac-Man clone written in C using raylib for rendering/input/audio. See `README.md` for project overview, controls, and game states.

## Build Commands

```bash
# Configure (from project root)
cmake -B build

# Build
cmake --build build

# Run (MSVC puts exe under Debug/)
./build/pac_man/Debug/pac_man
```

No tests or linter — the build is the only verification step. The build copies `src/resources/` into the output directory automatically.

## Architecture

- **Language:** C (no C++), linked against raylib
- **Build system:** CMake, with raylib vendored under `vendor/raylib/`
- **Source layout:** All `.c` and `.h` files live under `src/` (recursively globbed by CMake). Game assets go in `src/resources/`.
- **Window:** 800x1000, 24px tile grid (28x36), 60 FPS
- **Input:** keyboard (arrow keys, WASD) and gamepad (left stick, D-pad) simultaneously
- **Visual style:** modernized — neon glow, rounded walls, particle effects, dark background. Not pixel-art retro.

### Key design patterns

- One `Game` struct holds all state, passed by pointer. No heap allocation.
- Each module owns its struct and logic; `game.c` orchestrates them. Modules take only the fields they need (e.g. `pacman_update` takes level and frightened flag, not the whole Game).
- `game_update()` dispatches to one handler function per game state (`update_title`, `update_playing`, `update_dying`, etc.). `game_draw()` has a similar per-state switch.
- Ghost AI uses tile-based pathfinding: at each intersection, evaluate non-reverse directions, pick smallest Euclidean distance to target. Tie-break: Up > Left > Down > Right.
- **Level tier pattern:** multiple functions (`speed_tier`, `elroy_tier`, `scatter_chase_tier`, `ghost_house_tier`, `fright_level_index`) map a level number to an index into `static const` data tables. This is how all level-dependent difficulty scaling works. When adding level-dependent behavior, follow this pattern.
- Maze walkability has three variants: `maze_is_walkable` (general), `maze_is_walkable_pacman` (blocks ghost door), `maze_is_walkable_ghost` (allows ghost door for EXITING/EATEN modes).
- Maze wall edges are precomputed into `Game.wall_flags[][]` (a bitmask per tile) at level start. `draw_maze()` reads these flags instead of recalculating neighbor checks per frame.
- Shared data that multiple modules need (elroy thresholds, direction vectors) is declared in `common.h` and defined in `maze.c`. Module-specific tables stay `static const` in their own `.c` file.
- All graphics are procedural (raylib draw calls). Sound effects are WAV files in `src/resources/` generated by rfxgen.

### Important caveats

- `DIR_NONE` is -1, but `dir_dx`/`dir_dy` arrays have 4 elements (indexed 0-3). Always guard with `if (dir != DIR_NONE)` before using direction as an array index — otherwise it's undefined behavior.
- Named constants for all tunable values live in `common.h` (`#define`). New magic numbers should be added there, not hardcoded inline.

## Coding principles

- **C game programming best practices** — prefer stack allocation over heap, use fixed-size arrays where possible, keep hot data contiguous, avoid unnecessary indirection.
- **KISS** — simplest thing that works. No clever patterns where a plain `if` does the job.
- **YAGNI** — don't build for hypothetical needs. No abstraction layers "for later."
- **DRY** — remove real duplication, not shape-similar code. Wrong abstraction costs more than repetition.

When in doubt, lean KISS over DRY.

## Sound Generation

Generate game sounds with rfxgen (by the raylib author).

```bash
# Available presets: coin, laser, explosion, powerup, hit, jump, blip
"D:/rfxgen_v5.0_win_x64/rfxgen.exe" -g coin -o sound.wav
```

Store WAV files in `src/resources/`.
